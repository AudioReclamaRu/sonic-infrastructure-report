# feed/ — редакционный слой публикаций (TG-first)

Это **издательский контур** канала: расписание, редакционные концепты, обложки.
Публикация выполняется автономным лупом `publisher.py --loop` (TG-first,
идемпотентность по `event_key` и каноническому событию), а не руками.

## Файлы

| Файл | Роль |
|---|---|
| `items.csv` | Расписание. Строка: `pubDate~~~title~~~desc~~~source~~~guid~~~img~~~event_key` (7 полей для новых материалов; 6 полей сохранены для legacy. `event_key` стабилен для одного события, даже если меняются заголовок, источник, `guid` или обложка) |
| `concepts.json` | Редакционные концепты: `{guid: {headline, demo, explain, consequence, visual_object, cover_prompt, demo_shift, object_type, cover_test}}` — **гейт публикации**, 9 полей (см. ниже); опционально `event_object` + `article_structure` (Level B) |
| `image_gen.py` | Version-aware генератор обложек (RED FIELD, арт-директор). CLI: `--verify / --rebuild / --force / --guid` |
| `images/manifest.json` | Единственный источник истины по обложкам (см. контракт ниже) |
| `tests/` | Тесты контракта генератора (`test_image_gen_versioning.py`) |

## Идентичность события и защита от дублей

`guid` — идентификатор строки расписания, а не новости. Поэтому он не может быть единственным ключом идемпотентности.

Для каждой новой новости задаётся стабильный `event_key`, например `us-campaign-ad-lowest-rate-party-committees-2026-10-28`. Любые переформулировки, обновлённые заголовки, новые обложки и альтернативные источники одного события используют тот же ключ. Внутри Telegram это одна запись, которую нужно редактировать, а не публиковать заново.

Перед отправкой `publication_guard.py` выполняет последовательные проверки:
1. совпадение `event_key`;
2. совпадение нормализованного канонического URL источника;
3. совпадение fingerprint видимого текста;
4. близкое текстовое совпадение — переводит запись в `REVIEW_REQUIRED`, не отправляя её автоматически.

SQLite-журнал `tg/publication-ledger.sqlite3` — долговременная запись попыток. Статусы:
- `SENDING` — намерение записано до сетевого запроса;
- `SENT` — Telegram вернул успешный ответ и message_id сохранён;
- `FAILED` — Telegram однозначно отказал; после исправления допустим повтор;
- `UNKNOWN` — тайм-аут/обрыв/неразбираемый ответ. Автоматический повтор запрещён, потому что Telegram мог принять сообщение.

**Точная гарантия:** Bot API не предоставляет ключ идемпотентности для `sendMessage`/`sendPhoto`. Поэтому система обеспечивает консервативный at-most-once send attempt, а не обещает невозможное exactly-once. Неопределённую попытку нужно сверить с каналом и вручную разрешить через `tools/reconcile_telegram_publication.py`. Не удалять этот SQLite-файл при очистке логов.

Legacy-строки с шестью полями сохраняются. При первом запуске журнал гидратируется данными `tg_published.txt` и `tg_state.txt`, когда соответствующая строка ещё присутствует в расписании. Это не восстанавливает историю, которую оператор удалил и из канала, и из локальных tracker-файлов; перед новой миграцией старую историю нужно сохранить.

## Иностранные названия и аббревиатуры

Новые материалы используют `editorial_version: 2` и машинный словарь `abbreviations`. Иностранное сокращение либо расшифровывается перед первым употреблением, либо остаётся в исходном написании латиницей. Фонетическая транслитерация запрещена. См. `standards/foreign-abbreviation-and-name-policy.md`.

## Единица публикации — ДЕМОНСТРАЦИЯ (не тезис)

Единица публикации — **демонстрация**: реальный факт (исследование, кейс,
событие), который читатель **не мог знать минуту назад**. Не тезис, не
рассуждение, не «мы решили написать о голосе».

Порядок поста — аннотация редактора (решение 25.09.2026):

> **Демонстрация → неожиданность → объяснение → следствие.**

- Заголовок (`headline`) — **неожиданность** сдвига, которую показывает демонстрация.
- `demo` — уникальный факт: цифры, дата, название исследования, конкретный кейс. Идёт в посте первым, открывает доказательство.
- `explain` — почему этот факт меняет картину мира читателя.
- `consequence` — что это значит для бизнеса/выбора голоса.

Автопроверка (пример): в `demo` обязана быть **конкретика** — цифра/процент/дата/
название, иначе пост не даёт читателю нового → REJECT.

## Редакционный гейт (обязательный слой концептов)

Пост публикуется **только** если в `concepts.json` заполнены **все девять полей**
(источник истины — `publisher.py:109` `REQ_CONCEPT_FIELDS`):

- `headline` — неожиданность (заголовок несёт конфликт/сюрприз, а не тему)
- `demo` — демонстрация с конкретикой (цифры/даты/названия; открывает доказательство)
- `explain` — объяснение: почему это меняет привычную картину
- `consequence` — следствие для читателя/бизнеса
- `visual_object` — что запомнится через неделю (конкретный предмет кадра)
- `cover_prompt` — как снять именно этот предмет
- `demo_shift` — что меняет сама демонстрация (сдвиг, который она показывает)
- `object_type` — тип изменения (см. `standards/editorial-object-contract.md`)
- `cover_test` — чего обложка НЕ должна быть (как самопроверка кадра)

Для новых материалов `editorial_version: 2` дополнительно обязателен стабильный `event_key`; машинный шлюз проверяет все видимые латинские акронимы по `abbreviations` и запрещённые фонетические варианты.

Плюс необязательный слой Level B (аддитивно, только если поле присутствует):
`event_object` (8 полей) + `article_structure` — Editorial Object System,
контракт `standards/editorial-object-contract.md`. Тогда `publisher.py`
дополнительно считает 4 вердикта и пишет `state/editorial.jsonl`.
Концепты без `event_object` работают как раньше.

### Гейт источника (железобетонно)

Ссылка `src` в `items.csv` обязана вести на **реально существующий локальный
документ** в репозитории (evidence/corpus/guides/reports). Проверка
`source_resolves()` в `publisher.py`: путь после `/blob/<ref>/` собирается в
локальный путь `REPO/...` и обязан `os.path.isfile()`. Фантомные доказательства
(ссылка на несуществующий файл/репозиторий) → полный REJECT: слот не публикуется,
даже если концепт заполнен.

### Финальный редакционный фильтр

Перед публикацией обязателен вопрос:

> **«Что читатель увидит нового, чего он не видел минуту назад?»**
> Если ответ «ничего» — публикация не выходит. Даже если E-документ существует,
> QA зелёный и обложка сгенерирована.

Правило **«один документ = один пост» отменено**. Несколько демонстраций из
одного документа допустимы; одна демонстрация, распиленная на N постов без
нового факта, — нет.

### Механика гейта

Если поля не заполнены (или источник фантомный) — REJECT: guid замораживается в
`state/rejected.txt` (не потребляет дневной лимит TG, не спамит циклами).
Как только концепт заполнен — заморозка снимается автоматически.

Заголовок поста = `headline`. Тело строится по формуле:
`demo` → `explain` → `consequence` (+ `desc` из `items.csv` как нижний слой).
Рекламных хвостов (CTA, контакты, хэштеги) в постах нет.

## Обложки: version-aware RED FIELD (арт-директор)

- `DESIGN_VERSION` в `image_gen.py` — текущая версия визуального языка.
- `images/manifest.json`: `{guid: {design_version, asset_hash, generated_at, path, visual_object?}}`.
- `path` — **POSIX-стиль** (`feed/images/<name>.png`, `/`, не `\`).
- `ASSET_HASH = SHA256(CONTENT_ID + ":" + DESIGN_VERSION)` — без seed; изменение
  визуального языка = bump `DESIGN_VERSION` = автоматический перевыпуск всех
  обложек, устаревшие PNG уходят в `images/backup-red-field/`.
- PNG не может оставаться актуальным только по факту существования файла —
  нужен манифест (version + hash), совпадающий с кодом.
- У каждой новости, которая прошла гейт, — **один визуальный объект**
  (`visual_object` из концепта): красный — акцент, а не заливка.
- Уникальность: новый кадр сравнивается dHash с последними 20 обложками; если
  слишком похож — авто-твист кадра (до 6 попыток).
- На картинке нет текста: чёрное поле, сигнал, предмет.

CLI (проверки перед рестартом / после правок):
```
python feed/image_gen.py --verify     # stale=0 + exit 0 — всё актуально
python feed/image_gen.py --rebuild    # перевыпуск только устаревших
tools/check-covers.ps1                # unittest + --verify (CI)
```
