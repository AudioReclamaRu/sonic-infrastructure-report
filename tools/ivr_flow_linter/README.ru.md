# Проверка логики IVR-меню: IVR Flow Linter

**IVR Flow Linter** — небольшой инструмент на Python без сторонних библиотек. Он проверяет JSON-описание схемы голосового меню до передачи в интеграцию с АТС: существуют ли переходы, нет ли тупиков, доступны ли узлы из начальной точки, предусмотрены ли реакции на молчание и неверный ввод.

Он отвечает на узкий вопрос: **не содержит ли заявленная схема маршрутов структурных ошибок?**

Это предварительная статическая проверка, а не тест реального телефонного номера или работающей АТС.

## Что проверяет линтер

- все начальные точки (entrypoints) объявлены в списке узлов;
- каждый переход указывает на существующий узел;
- идентификаторы узлов не повторяются;
- в JSON нет дублирующихся ключей, которые парсер мог бы незаметно перезаписать;
- для меню заданы переходы при тайм-ауте и неверном вводе, если этого требует политика проекта;
- каждый достижимый узел может привести к конечному исходу;
- недостижимые узлы отмечаются предупреждением;
- при включённом требовании доступен маршрут к оператору;
- циклы помечаются для отдельной проверки ограничений повторов и возврата.

Требования задаются в поле `policy`. Линтер не навязывает один универсальный сценарий для всех компаний и АТС.

## Установка и запуск

Требуется Python 3.10 или новее. Дополнительные пакеты не нужны.

Из корня репозитория:

```bash
python tools/ivr_flow_linter/ivr_flow_lint.py tools/ivr_flow_linter/examples/valid-flow.json
```

Машиночитаемый результат для CI или другой программы:

```bash
python tools/ivr_flow_linter/ivr_flow_lint.py tools/ivr_flow_linter/examples/valid-flow.json --json
```

Коды завершения процесса:

| Код | Значение |
|---:|---|
| 0 | ошибок графа не обнаружено; предупреждения возможны |
| 1 | найдены ошибки в объявленной схеме |
| 2 | входной файл не прочитан или JSON некорректен |

## Как описать схему

Входной формат — JSON. Контракт полей находится в [JSON Schema](schema/ivr-flow.schema.json).

- `entrypoints` — начальные узлы, с которых может начаться сценарий.
- `nodes` — меню, информационные сообщения и конечные исходы.
- `transitions` — соответствие события (например, клавиша 1, `timeout`, `invalid_input`) следующему ID узла.
- `policy` — обязательные проверки конкретного проекта.
- `terminal_kind` — тип конечного исхода: оператор, очередь, голосовая почта, завершение вызова и т. п.

Начните с [положительного синтетического примера](examples/valid-flow.json). [Отрицательный пример](examples/invalid-flow.json) намеренно содержит отсутствующую цель перехода, замкнутый цикл и недостижимый узел.

Оба примера вымышлены. Это не клиентские кейсы и не рекомендуемая готовая конфигурация для установки.

## Проверка самого инструмента

Запустить регрессионные тесты:

```bash
python -m unittest discover -s tools/ivr_flow_linter/tests -v
```

В CI репозитория проверяются оба сценария: положительный пример должен пройти, а отрицательный — быть отклонён.

## Что линтер не проверяет

Статус PASS **не означает**, что меню правильно работает для звонящего. Инструмент:

- не подключается к АТС и не читает конфигурацию конкретного производителя;
- не проверяет, что клавиша действительно настроена на указанный маршрут;
- не совершает звонки и не проигрывает аудиофайлы;
- не проверяет формат, громкость, произношение или качество записанных реплик;
- не оценивает понятность меню и не гарантирует доступность сценария;
- не подтверждает, что в реальной телефонной платформе корректно работают расписания, очередь и перевод.

Для выпуска меню всё равно нужны проверка тестового номера, проход всех пользовательских маршрутов, испытание молчания и неверного ввода, проверка рабочего/нерабочего времени и прослушивание через телефонный тракт. Эти требования описаны в [стандарте проектирования и выпуска IVR](../../problem-solutions/IVR_DESIGN_STANDARD.md).

## Чем отличается от смежных инструментов

- [Asterisk Call Flow Builder](https://github.com/michaelnabil230/asterisk-call-flow-builder) — визуальное проектирование сценариев Asterisk и экспорт dialplan.
- [MakingChatbots/ivr-tester](https://github.com/MakingChatbots/ivr-tester) — автоматизированные испытания реального телефонного сценария с вызовами и DTMF.
- [ossobv/asterisklint](https://github.com/ossobv/asterisklint) — проверка конфигурации и dialplan Asterisk.

Эти подходы не взаимозаменяемы. Статический граф можно проверить до генерации или настройки dialplan, затем отдельно проверить конфигурацию АТС и провести испытание реального вызова.

## Лицензия и происхождение

Материалы репозитория распространяются на условиях корневой лицензии CC BY 4.0 с обязательной атрибуцией. Перед повторным использованием следует проверить лицензию и ограничения своих сторонних компонентов.

Линтер реализует только часть внутреннего стандарта IVR: явные fallback-маршруты, отсутствие структурных тупиков и возможность выхода к оператору, если это требуется проекту. Статическая проверка не заменяет профессиональную проверку сценария и реальный запуск тестового вызова.


## Интеграция с существующими IVR-инструментами (experimental)

Это два отдельных адаптера, а не один универсальный коннектор.

### Asterisk Call Flow Builder → IVR Flow Linter

Файл interop/acfb_to_flow.py преобразует наблюдаемую в исходном коде Asterisk Call Flow Builder модель graph JSON версии 1 в канонический IVR Flow JSON версии 1. Поддерживается fail-closed подмножество узлов: start, menu, playback, extension, queue и hangup. Неизвестный тип, дублирующий выход, отсутствующая ссылка или иной version блокируют конвертацию.

На проверенном commit 0ea0693df66217241f5ea62dd512d3a923e6325f модель graph строится внутри приложения, но штатная кнопка JSON-экспорта не обнаружена: публичный экспорт выдаёт extensions.conf, сериализация graph JSON в коде закомментирована. Поэтому fixture в examples — синтетическая реконструкция наблюдаемого формата, а не файл, полученный из работающей установки. Для пользовательского handoff потребуется отдельный JSON export upstream или явное получение этого объекта из приложения.

Запуск из корня репозитория:

    python tools/ivr_flow_linter/interop/acfb_to_flow.py tools/ivr_flow_linter/examples/asterisk-call-flow-builder.graph.synthetic.json --output /tmp/ivr-flow.json
    python tools/ivr_flow_linter/ivr_flow_lint.py /tmp/ivr-flow.json

Особая осторожность: в просмотренном ACFB exporter узел extension следует только по exits[0], а queue выбирает один target по фиксированному приоритету handle. При нескольких выходах адаптер сохраняет все рёбра объявленного графа и печатает WARNING, но это не доказывает, что сгенерированный extensions.conf сохраняет все ветви. PASS graph lint не является проверкой эквивалентности Asterisk dialplan.

### IVR Flow → MakingChatbots/ivr-tester scenario plan

Файл interop/flow_to_ivr_tester_plan.py превращает проверенный канонический граф в матрицу путей и действий, совместимую по смыслу с проверенным API MakingChatbots/ivr-tester: Scenario и Step.

Запуск:

    python tools/ivr_flow_linter/interop/flow_to_ivr_tester_plan.py /tmp/ivr-flow.json --output /tmp/ivr-tester-plan.json

Соответствия:
- DTMF digit → then.press(digit);
- timeout → then.doNothing();
- invalid_input → then.press(first unused key from 0123456789), если такой ключ остался;
- обычное сообщение / continue → then.doNothing();
- исходы extension/queue, не представленные API IVR Tester, фиксируются как manual_routes, а не выдаются за автоматизированный тест.

План намеренно содержит expected_prompt_transcript: null и runtime_ready: false. Значение whenPrompt в реальном IVR Tester должно быть функцией, построенной по фактической распознанной реплике. Нельзя подставлять имя аудио, имя файла или Asterisk playback token вместо услышанного текста. Для запуска потребуются реальные from/to numbers, учётные данные и настройки распознавания; они в репозитории не хранятся.

Параметры silence-after-prompt и timeout имеют значения по умолчанию 3000 и 6000 мс, как в проверенном примере README IVR Tester; при практическом прогоне их нужно сверить с настройками тестового номера.

### AsteriskLint — следующий, отдельный слой

После получения конкретного extensions.conf можно отдельно установить AsteriskLint и запустить:

    asterisklint dialplan-check extensions.conf

AsteriskLint проверяет конфигурацию и dialplan Asterisk, а не наш абстрактный graph. Это отдельный GPLv3+ проект, он не копируется в этот репозиторий и не становится обязательной зависимостью.

### Границы совместимости

- Эти адаптеры проверяются на синтетических fixture и контрактных unit tests. Живого звонка, Asterisk PBX, Twilio и реальных записей в этом change set нет.
- Формат Asterisk Builder реконструирован по открытому исходному коду указанного commit; пока у самого приложения нет штатного JSON export, путь handoff не является кнопкой-в-кнопку.
- Схема канонического графа остаётся независимой от Asterisk, IVR Tester и бренда.
- Подробный аудит и решение по upstream находятся в research/IVR_INTEROP_TOOLCHAIN_AUDIT_2026-11-14.md и research/UPSTREAM_PROPOSAL_ASTERISK_CALL_FLOW_BUILDER_JSON_EXPORT_2026-11-14.md.
- Ни один из внешних проектов не одобрял и не подтверждал эту интеграцию.


### Происхождение и перенос параметров узлов

Конвертер сохраняет provenance всего потока и interop_source для каждого перенесённого узла. В metadata попадает только whitelist полей, относящихся к типу узла: например extension/ringSeconds для добавочного номера и queue_name/strategy/timeout для очереди. Координаты canvas сохраняются отдельно. Произвольные поля, в том числе потенциально секретные, не копируются. Это не полный round-trip ACFB graph: для обратного восстановления исходной схемы нужен исходный graph JSON и будущий штатный JSON export.
