# Реестр идентификаторов доказательств

evidence/ID_REGISTRY.csv — единственный реестр занятых и зарезервированных ID карточек evidence/E-2026-NNN.md.

## Зачем он нужен

Идентификатор доказательства — стабильный адрес записи, на который ссылаются другие файлы. Два разных наблюдения не могут иметь один ID, даже если находятся в разных открытых pull request. Проверка одного PR сама по себе не обнаруживает коллизию с другой независимой веткой.

Реестр содержит как уже существующие записи, так и резервации открытых веток. Резервация не утверждает, что доказательство уже слито в main; она закрепляет ID за конкретной веткой до слияния.

## Поля

| Поле | Значение |
|---|---|
| evidence_id | Уникальный ID вида E-2026-107 |
| path | Единственный допустимый путь карточки |
| allocated_branch | main для исторической записи либо точное имя ветки, которой закреплён ID |
| notes | Краткое назначение или происхождение резервации |

allocated_branch — это происхождение/владелец резервации, а не текущий статус файла. После слияния исходная ветка остаётся в истории реестра.

## Правило создания новой карточки

1. Сначала выбери свободный ID, которого нет в реестре, а не просто максимальный номер в локальной копии.
2. Создай рабочую ветку.
3. Добавь строку с новым ID в ID_REGISTRY.csv, указав точное имя ветки в allocated_branch.
4. В той же ветке создай карточку evidence/E-2026-NNN.md; id в YAML frontmatter обязан совпадать с именем файла.
5. Запусти python tools/validate_evidence_id_registry.py.
6. В pull request CI дополнительно проверит, что новые evidence-файлы добавляет именно ветка, зарезервировавшая их ID.

Не перенумеровывать существующую запись только ради удобства. Если выявлена коллизия, сначала установить исторического владельца ID, затем перенести только конфликтующую карточку и все ссылки на неё.

## Текущие резервации

Реестр создан 19.11.2026 по main и проверенным открытым PR. Он закрепляет диапазоны E-066…E-107 за существующими ветками; закрытые и заменённые PR #63 и #64 в резервации не входят. Содержимое и состояние веток проверяются отдельно — запись о резерве не равна доказательству успешного CI или слияния.
